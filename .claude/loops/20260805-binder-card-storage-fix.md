# バインダーのカード収納位置修正 + 収納OKエフェクト + ページめくり + カード取り出し

## 目的
1. カードをバインダーに収納したとき、実物モデル（CardBinder.fbx）のポケット位置にぴったり収まるようにする。
2. カードをバインダーに近づけた際、収納できる状態かどうかを光る/アウトライン等の視覚効果でわかりやすくする。
3. （上記1の対応に伴うスコープ）1ページに収まらない分はページをめくって収納・閲覧できるようにする。実物モデルが既に8枚の個別ページ（ヒンジ回転可能な設計）を持っているため、今回は本物の3Dページめくりアニメーションとして実装する。
4. バインダー内のカードをゲインのために取り出す経路（`CardBinder.TryTakeOut`）が現状どこからも呼ばれておらず未接続なので、これを接続する。あわせて、接続時に露呈する既存の潜在バグ2件を修正する。

## 根本原因（調査結果）
`Assets/_Content/Models/CardBinder.fbx` をバイナリ解析し、実測した結果：

- モデルは `Cover_Front` / `Cover_Back` / `Spine` / `Binder_Rings` / `Page_01`〜`Page_08`（8ページ）で構成される。
- 各 `Page_XX` のメッシュ境界（モデルローカル座標、`BinderView` が `Model` に適用する `Euler(-90,0,0)` 回転の**前**の値）は
  - X（見開き幅方向）: `-0.007 〜 0.214`（幅 0.221m = 221mm）
  - Z（ページ縦方向）: `-0.145 〜 0.145`（高さ 0.290m = 290mm）
  - Y（ページ積層厚み）: ページごとに約1.4mmずつオフセット（8枚積層）
- `.claude/agent-memory/blender-mcp-learnings.md` の制作メモ（8章）によれば、このページは「スロット63×88mm（トレカ実寸）× 3列 × 3行」で設計されている。実測値 221mm ÷ 3 ≈ 73.7mm、290mm ÷ 3 ≈ 96.7mm のセルピッチは、63×88mmカード＋マージン（横10.7mm・縦8.7mm）という設計と一致する。
- `CardVisualFactory.cs` の `CardWidth = 0.063f` / `CardHeight = 0.088f` は、まさにこの実寸トレカサイズで作られている（つまりカードとバインダーは元々サイズが合致するように設計されていたが、`BinderView` 側だけ旧プレースホルダー時代の定数のまま更新されていなかった）。
- **現行コードの問題**: `BinderView.GridPosition()` は `ColumnsPerPage=4, RowsPerPage=5`（1ページ20マス）を「page0=左（X=-0.14）」「page1=右（X=+0.14）」の2ページ分、計40マスに割り当てている。しかし実物モデルにX=-0.14付近の「左ページ」は存在せず（そこは `Cover_Front`＝ポケットのない表紙裏）、実在する唯一のページ（現在開いているページ）はX=[-0.007, 0.214]の範囲にしかない。かつ分割数も4×5ではなく3×3が正しい。これが「ポケットからズレる」の直接原因。

## 受け入れ基準
- [ ] `BinderView` のミニカードグリッドが、実測値ベースの3×3グリッド（ページ中心X≈0.1035、セル幅≈0.0737m、セル高≈0.0967m、原点は現在開いているページのローカル座標系）でカードを配置する。定数はマジックナンバーではなく、上記実測値から算出したものであることがコメントでわかるようにする。
- [ ] ミニカードのスケールは、`CardVisualFactory` の実寸（0.063×0.088m）とセルサイズの比率をふまえて調整し、セル内に自然に収まる（食み出さない・小さすぎない）。
- [ ] `CardBinder` の収納上限が「8ページ×9ポケット = 72枚」になる（page/slotのハードコーディングではなく、ページ数×9で算出する）。
- [ ] `BinderView` に「現在開いているページ」の概念が追加され、そのページに属するカードのみがグリッド表示される（挿入順で `index / 9` = ページ、`index % 9` = スロットとして割り当てるシンプルな方式でよい。カードが取り出されて配列が詰まった結果、後続カードのページ表示が変わることは許容する＝固定スロット保持は今回のスコープ外）。
- [ ] **ページめくり（実体アニメーション）**: 常に「現在の最前面ページ」と「（あれば）直前にめくって左側にある1枚」の**2枚だけ**が掴み判定を持つ。他の6枚には一切当たり判定を付けず、複数ページを誤ってまとめて掴むことは構造的に起こらない。
  - 掴み起点は各ページの**メッシュ境界のわずかに外側に置いた仮想の「角タブ」**（ページ実メッシュはX∈[-0.007, 0.214] / Z∈[-0.145, 0.145]なので、それより外側、例えばX≈0.225付近にある小さな判定点。ポケット領域（3×3グリッドはページ境界ぎりぎりまで埋まる）と物理的に重ならない設計にすること。この重なり回避が最重要）。
  - ピンチが角タブ近傍で始まったら、ページのヒンジ回転（背表紙軸＝実測でモデルローカルZ軸）をピンチ位置の動きに追従させる。指を離した時点の回転角がしきい値を超えていれば180°まで自動補完してめくり切り`currentPageIndex`を更新、しきい値未満ならバネで元に戻す。
  - ピンチ開始時、先にミニカード（後述の取り出し判定）の近傍かどうかを確認し、ミニカードが優先的にマッチした場合はページめくり判定を行わない（角タブがポケット領域と重ならない設計により、通常はそもそも競合しない想定。優先順位はあくまで保険）。
- [ ] **カードの取り出し（ゲイン導線の接続）**: ミニカードにColliderを追加するのではなく、ピンチ開始位置と「現在ページに表示中のミニカードのTransform」との距離判定で最寄りのミニカードを検出する。ヒットしたら `CardBinder.TryTakeOut` → 即座にその手の `CardGrabInteractor` 経由で `TryGrab()` し、実寸カードとしてHeld状態にする（既存の両手引き裂きゲインジェスチャーがそのまま使える）。ポーク動作や「ゲインしますか？」等のテキスト確認UIは追加しない。取り出したカードをバインダーの収納圏内で離せば、既存の `TryStore` 経路でそのまま再収納できる。
- [ ] **バグ修正1**: `StoreCopy`（「錬金キット」等の効果で複製収納されたカード。`CardInstance.Source == null`）は取り出し操作の対象から除外する（`TryTakeOut` 呼び出し前、または `TryTakeOut` 内部でSource有無をチェックし、Source==nullなら取り出し不可としてfalseを返す）。誤って取り出そうとしてカードが無言で消滅することを防ぐ。
- [ ] **バグ修正2**: `CardizableItemBase.ReleaseFromBinder` が呼ばれる際（＝バインダーから取り出された際）、1分ルールの消滅カウントダウンを無条件にフルリセット再始動しないようにする。取り出してすぐゲインしようとしているだけなのに、もたついたら消滅する仕様は理不尽なため。方針: 取り出し直後はカウントダウンを一時停止した状態にし、（a）掴んでいる間は停止のまま、（b）ゲインもバインダーへの再収納もせずに手を離した場合のみ、その時点からカウントダウンを再開する。
- [ ] カードを掴んでいる間、そのカードがいずれかの `CardBinder.IsInStoreRange` 圏内に入ると、そのバインダーが発光（エミッション強調）またはアウトライン表示される。圏外に出る／収納が完了すると通常表示に戻る。
- [ ] ハイライト用のマテリアル操作は `renderer.material`（インスタンス化）または `MaterialPropertyBlock` を使い、`sharedMaterial` を直接書き換えない（マルチプレイヤーで他プレイヤーのバインダーに影響しないため）。
- [ ] 既存の `TryStore` / `TryTakeOut` / `TryConvertCard` / `StoreCopy` / `Clear` / `DiscardRandom` / `CardStored` 等のAPIとR3購読チェーンを壊さない。UniTask / R3 / DOTween の利用規約を守り、`Coroutine` / `UnityEvent` / `event Action` を使わない。
- [ ] EditModeテストで検証可能な範囲（グリッド座標計算、capacity算出、ページ/スロットindex算出、角タブとポケット領域の非重なり、収納圏内判定によるハイライトON/OFFの状態遷移、StoreCopyカードの取り出し拒否、取り出し時にカウントダウンが即座に再始動しないこと）をテストする。

## 変更対象
- `Assets/_Content/Scripts/GIPoker/CardBinder.cs`: `capacity` を `pageCount(8) * SlotsPerPage(9) = 72` に変更。ページ数・1ページあたりスロット数を定数化。`TryTakeOut` にSource==nullガードを追加。
- `Assets/_Content/Scripts/GIPoker/CardizableItemBase.cs`: `ReleaseFromBinder` のカウントダウン再始動方針を変更（取り出し直後は一時停止、掴み続けている間は停止のまま、手放して未収納・未ゲインのまま放置された場合のみ再開）。
- `Assets/_Content/Scripts/GIPoker/BinderView.cs`: `GridPosition()` を実測値ベースの3×3グリッドに書き換え。現在ページ管理・ページめくり（角タブ起点のヒンジ回転追従＋しきい値コミット）・収納OKハイライトの購読とマテリアル制御を追加。ミニカードのTransformリストを外部（CardGrabInteractor側）から距離判定できるように公開する。
- 新規ジェスチャー/入力コンポーネントが必要な場合は `Assets/_Content/Scripts/GIPoker/` 配下に追加（`HandPinchTracker` 等の既存の購読可能なトラッカーがあれば流用する。既存実装を先に調査してから決めること）。
- `Assets/_Content/Scripts/GIPoker/CardGrabInteractor.cs`: ピンチ開始時に「浮遊カード（既存）→バインダー内ミニカード（新規）→ページ角タブ（新規）」の優先順位でヒット判定するように拡張。保持中カード位置を毎フレーム最寄りのバインダーへ通知する呼び出しを追加（ハイライト判定のトリガー）。

## やらないこと（スコープ外）
- カードの固定スロット保持（取り出し後も他カードの表示ページ・スロットが変わらないようにする仕組み）。
- 収納上限72枚を超えるゲームバランス調整（種類ごとの出現上限は `GI_POKER_PLAN.md` の値のまま変更しない。バインダー容量が72に増えるだけで、実際に集まる想定枚数はプラン記載の出現上限内に収まる）。
- 実機（PICO）でのハンドトラッキングジェスチャーの実操作感チューニング（角タブの当たり判定半径やしきい値角度の微調整）。
- ページを戻す方向のめくり（直前の1枚）を含め、3枚以上遡ってページを一気に移動するショートカット操作。

## 制約
- 規約: UniTask / R3 / DOTween、ハンドトラッキング専用（コントローラー入力禁止）、`.unity`/`.prefab`/`.asset` は直接編集禁止（今回は `.cs` のみの変更なのでuloop経由のシーン編集は不要な想定。もしプレハブ調整が必要になった場合は `uloop-execute-dynamic-code` 経由で行うこと）。
- **このセッションの実行環境にはUnity Editorがインストールされていない**ため、`uloop`経由のコンパイル確認・PlayMode目視確認ができない。実装はC#の静的レビュー・数式検証（座標計算の手計算/EditModeテストでの検証）のみで進める。最終的な見た目確認（グリッド位置が本当にポケット絵にぴったり合うか、発光エフェクトの見え方、ページ送りジェスチャーの操作感）は、ユーザーのローカルUnity環境での確認が別途必要。

## 検証方法
- EditModeテスト: `BinderView` のグリッド座標計算をテスト可能な形に切り出し、既知の col/row/page に対する期待座標をアサートする。`CardBinder.capacity` が72であること、`TryStore` が73枚目を拒否すること。ページ/スロットindex算出（`index/9`, `index%9`）の境界値テスト。ハイライトのR3プロパティが「保持中カード close→true」「離れる/収納→false」の状態遷移をすること。
- 静的レビュー: `git diff` の目視、規約違反の機械チェック（`StartCoroutine`/`IEnumerator`/`UnityEvent`/`event Action`/`yield return` のgrep）、`code-reviewer` エージェントによる独立レビュー。
- PlayMode/目視確認: **今回は実施しない**（Unity Editor未インストールのため）。PR本文に「実機/ローカルUnity環境での確認が必要」と明記する。

## 実機確認が必要な項目
- ミニカードが実際にポケット絵の枠内にぴったり収まって見えるか（実測値ベースの計算だが、ページのローカル座標軸の符号・原点の解釈にズレがあった場合は微調整が必要）。
- 収納OKの発光/アウトライン表現が、パススルーMR環境下で十分視認できる明るさ・コントラストか。
- ページ送りジェスチャーが誤爆せず直感的に操作できるか。
- **`BinderView.LoadPages` の `Transform.Find` は非再帰（直下の子のみ検索）**。`CardBinderModelPrefab` の実際のインポート階層が「Model直下にPage_01〜08が並ぶ」という前提からズレている場合（例: 中間グループに包まれている等）、該当ページが見つからず警告ログのみでページめくり・グリッド表示全体が静かに機能しなくなる。Unityで実際に開いた際、コンソールに `[BinderView] モデル内に Page_01〜Page_08 のうち...` の警告が出ていないか必ず確認すること。
- **収納OKハイライトは `_EmissionColor` プロパティ（URP Lit想定）に依存**している。`CardBinderModelPrefab` の実際のマテリアルがURP Lit以外（Simple Lit・カスタムシェーダー等）の場合、例外は出ないが発光が一切見えない可能性がある。実機確認時に光り方を目視すること。
