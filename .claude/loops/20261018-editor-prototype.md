# 試作（エディタ）: 同期・送信上限・追従（S-2〜S-4）とシミュレーターの取り込み

Issue: #36 ／ ブランチ: `repo/feature-editor-prototype`（`repo/develop` から作成済み）
設計書: `TREASURE_HAUL_DESIGN.md` 第6版 11章・12章・4.3・6章・6.2

## 目的
実機（PICO）が10月中まで使えないため、エディタで確かめられる【要検証】項目（S-2・S-3・S-4）を先に確かめ、設計書の方式と値を決める。
あわせて、エディタで手を動かして検証できる環境（XRI のシミュレーター）を整える。ここで作る「手の観測シーン」は、実機が届いたら #49（S-1）でそのまま使う。

## 受け入れ基準

### A. シミュレーターと手の観測
- [ ] XR Interaction Toolkit 3.3.1 のサンプル「XR Interaction Simulator」が `Assets/Samples/` に取り込まれている（Package Manager の Sample の Import を使う。パッケージ構成は変えない）
- [ ] 試作シーン `TH_Proto_Hands` を Play し、シミュレーターで左右の手を出して手の形を「Open」→「Fist」に切り替えたとき、`XRHandSubsystem` から取った関節で計算した**握りの強さ（0〜1）**が、Open で低く（目安 0.3 未満）Fist で高く（目安 0.7 超）なることを、ログとスクリーンショットで確認できる
- [ ] 握りの強さはワールド空間のテキストにも出す（実機の #49 で、頭につけたまま読めるようにする）
- [ ] 握りの強さの計算は純粋な静的メソッド `FingerCurl`（関節の位置・向きの配列 → 0〜1）にし、EditMode テストで「伸ばした指＝低い」「曲げた指＝高い」「関節が足りない＝無効」を確かめる

### B. S-4 追従（エディタ・単体）
- [ ] 試作シーン `TH_Proto_Follow` に、重力なしの Rigidbody（interpolate、ContinuousSpeculative）を、決められた軌道で動く目標へ「位置は速度、向きは角速度」で追従させる仕組み（設計書 4.3、速度の上限〔追従速度の上限〕10m/s）と、固定の箱・壁を置く
- [ ] 自動で次の3つの軌道を流し、それぞれで **遅れ（障害物がないときの目標との距離の平均・最大）／めり込み（障害物の中に入った深さの最大）／ガタつき（障害物に押し付けている間の速度の向きの反転回数）** を測ってファイル（CSV）に書き出す: ①何もない所を往復、②壁に斜めに押し付けて沿わせる、③箱の角に押し付ける
- [ ] Fixed Timestep を 0.02秒（今の設定）・1/72秒・1/90秒 の3通りで測り、結果の表と推奨値を設計書 4.3（または 11章の結果欄）に書く。**プロジェクト設定の Fixed Timestep は変えない**（測定中だけ実行時に変え、終わったら戻す）

### C. S-3 送信の上限・大きさ・往復時間・再接続（エディタ＋クローン＋サーバー）
- [ ] NetSync サーバー（`uvx styly-netsync-server@<クライアントと同じ版>`）をこの Mac で起動し、エディタとクローン（2台目のエディタ）が同じ部屋につながる
- [ ] 試作シーン `TH_Proto_Net` の計測で、次を数値で記録する:
  - 往復時間: エディタ → クローンが送り返す → エディタ、の時間（100回の中央値・最大）
  - 送信の上限: 1秒に 20 / 30 / 50 回送ったとき、相手に届いた数と順番の入れ替わり、エディタのログに出る「Rate limited: dropped」の数。`ConfigureRpcLimit` で上限を上げた場合（例 60回/秒）も1回測る
  - 大きさ: 状態表 `ThItems` 相当（23個分、文字列）を1回の RPC で送れるか。あわせて 4KB・16KB・64KB で届くか
  - 再接続: サーバーを止めて再起動したとき、自動でつながり直すか、何秒かかるか、ClientNo が変わるか
  - グローバル変数: 片方が書いた値を、後からつないだ側が読めるか（設計書 3.2 の【要検証】）
  - DeviceId: クライアントから DeviceId を取れるか、どこで取れるか（設計書 3.3 の【要確認】）
- [ ] サーバー付属の疑似クライアント（`styly-netsync-simulator`）で接続を増やした状態（エディタ＋クローン＋疑似3台）でも、往復時間を1回測る

### D. S-2 持っているお宝の位置の同期（エディタ＋クローン）
- [ ] `TH_Proto_Net` に、`NetSyncObject` を付けたお宝の代わり（箱）を2つ置き、片方をエディタ、もう片方をクローンが持ち主になって動かす（スクリプトで決まった軌道）。相手の画面での **遅れ（送り手の位置との差）と、動きのなめらかさ（コマ飛び）** を記録する
- [ ] 持ち主の切り替え: `RequestOwnership` / `ReleaseOwnership` で持ち主を移したとき、何秒で切り替わるか、2台が同時に要求したらどうなるか、を記録する。ホストの承認（`ThGrabbed`）の後に持ち主を切り替える方式（設計書 6章）が成り立つかを結論として書く
- [ ] 持っているお宝どうしの衝突: 2つの箱を互いの軌道が交わるように動かし、両方の画面でどう見えるか（片方だけが衝突に気づくか、めり込むか）を記録する（スクリーンショット）

## 結果

計測はすべて同じ Mac の中（エディタ＋ParrelSync のクローン＋サーバー）。会場の Wi-Fi では遅れが増える。ログ・CSV は作業用の一時フォルダに置き、リポジトリには入れていない。

### A. シミュレーターと手の観測（達成）
| 手の形 | 左 | 右 |
| :--- | :---: | :---: |
| 既定（Resting） | 0.14 | 0.19 |
| Open | 0.04 | 0.03 |
| Fist | 1.00 | 0.98 |
- 握りの強さ = 人差し指〜小指の「関節の折れ角の合計」を 20°→0、180°→1 に直した値の平均（位置だけを使う）。`FingerCurlTests` 8件。
- XRI 3.3.1 のサンプルは、Grab / Thumb / Open / Fist の入力参照が壊れている（別サンプルを指している）。シーン側で付け替えて回避（学習メモに記録）。
- 力を抜いた手でも 0.14〜0.19 になる。実機のしきい値は #49 で決める。

### B. S-4 追従（達成。障害物に向かう成分を切る方式を採用）
| 押し付け | めり込み最大 baseline → sweep（mm） | 法線方向の揺れ（std mm） baseline → sweep |
| :--- | :--- | :--- |
| 壁 1m/s（0.02 / 1/72 / 1/90） | 33.0 / 27.8 / 25.5 → 14.7 / 29.2 / 12.7 | 13.5〜14.2 → 4.4〜13.4 |
| 壁 3m/s | 37.8 / 25.9 / 24.8 → 13.8 / 18.0 / 15.2 | 15.1〜17.0 → 5.9〜10.0 |
| 箱の角 1m/s・3m/s | 20.8〜29.0 → 0 | 5.2〜6.2 → 0.8〜2.2 |
- 何もない所の遅れは 0（追従速度の上限 10m/s を超える動きだけ遅れる）。すり抜けは全条件でなし。
- 壁で残るめり込みは主に回転による。速い手で壁に当てると小さな揺れの回数は増える。Fixed Timestep に一貫した差はなく、0.02秒のまま。
- 1回目の計測の「ガタつきほぼ0」は測り方の誤りだった（レビューで指摘、指標を直して取り直した）。

### C. S-3 通信（達成）
| 項目 | 結果 |
| :--- | :--- |
| 往復時間 | 中央値 約8ms（相手のフレーム待ちを除く）/ 約15ms（含む） |
| 送信の上限 | 30回/秒を超えると捨てる。`ConfigureRpcLimit` で上げると 100回/秒でも欠けない。順番の入れ替わり・重複なし。自分の RPC は自分にも届く |
| 大きさ | 状態表 23個分（約1,000文字）は問題なし。JSON 65,535 バイトを超えるとエラーなしで中身が空になる |
| 再接続 | サーバーが落ちても `IsReady` は true のまま。再起動後1秒以内に自動再接続、ClientNo は入れ替わる、停止中の RPC はまとめて届く |
| グローバル変数 | 後から入った端末も読める。1024 文字まで、書いた直後は読めない、サーバー再起動で消える |
| DeviceId | `NetSyncManager.Instance.DeviceId`、`GetDeviceIdByClientNo` / `GetClientNoByDeviceId` |
| 疑似3台を足して5台 | 往復時間はほぼ変わらない |

### D. S-2 位置の同期（達成。`NetSyncObject` は使わない判断）
| 送信頻度 | 相手の画面での定常の遅れ（p50） | 動き始め1秒時点 |
| :--- | :--- | :--- |
| 10Hz | 269〜288ms | 913〜968ms |
| 30Hz | 194〜210ms | 488〜915ms |
| 60Hz | 198〜221ms | 934〜938ms |
- 定常に戻るのは約8秒後。コマ飛びはなし。
- 持ち主の切り替えは約65ms。`RequestOwnership` は先着の調停をせず、同時の要求は後勝ち。
- 持っている箱どうしの正面衝突は、相手の画面で最大 4.5〜9cm めり込んで見え、その後は接したまま止まる。
- **判断**: MR では仲間の本物の手が見えるので、約1秒の遅れは許容できない。位置は RPC（片道 4〜12ms）にまとめて 30回/秒で送り、受け側で 0.05秒の補間をする方式に変更した（設計書 6章）。会場の Wi-Fi での確認は #38・#49・#45。

### 積み残し

- RPC で位置を送る方式の、会場 Wi-Fi・4台での遅れと欠け（設計書 6章【要検証】）
- クローンを GUI で起動すると ParrelSync のダイアログで止まる（人が ok を押すか、batchmode で動かす）
